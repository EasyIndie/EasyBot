# EasyBot 后续商用化推进路线图

> 基线：`codex/opt`，2026-07-30

## 1. 当前判断

EasyBot 的主要商用工程底座已经存在：

- 生产模式安全启动门禁、TLS 反向代理和生产专用部署清单；
- Secret 文件注入、非 root/只读容器、固定镜像摘要和供应链验证；
- liveness/readiness、优雅停机、Prometheus 指标和告警规则；
- PostgreSQL 与 `auth.db` 配对备份、恢复、保留和 schema 版本保护；
- API Key 生命周期、调用方配额、用量账本、审计链和隐私数据接口；
- 消息幂等、出站投递日志/outbox、财务事件账本和对账接口；
- SBOM、provenance、发布审批、release preflight 和商用上线证据门禁。

因此，后续主线不再是继续横向补通用能力，而是把已有能力放进真实生产环境，形成可审计的运行证据和真实客户闭环。

当前仍坚持 **每客户独立实例、独立数据库、独立密钥和独立备份**。在完成付费试点前，不建设进程内多租户 SaaS。

## 2. 五个阶段门

未通过当前阶段门，不开启下一阶段的大型工程任务。

### G0：冻结首个商用版本（1–2 天）

目标：确定唯一候选版本和首发服务范围。

执行：

1. 以当前提交运行：

   ```bash
   bash scripts/verify.sh --locked
   scripts/release-preflight.sh 0.0.26
   git diff --check
   ```

2. 确认首发只承诺经过真实账号验证的平台；平台限制写入销售说明。
3. 定义首个 SKU：
   - 独立托管实例；
   - API 请求额度；
   - 消息数据保留期；
   - 备份频率和恢复目标；
   - 支持时段和严重事件响应目标。
4. 冻结候选版本，候选期只接受 P0/P1 缺陷、安全和上线阻塞修复。

退出证据：

- 完整验证和 release preflight 日志；
- 候选 Git commit、tag 和不可变镜像 digest；
- 一页 SKU、平台能力边界和暂不支持清单，见 `docs/14 commercial-g0-scope.md`。

### G1：预生产环境验收（3–5 天）

目标：在与生产等价的环境中生成上线门禁要求的真实技术证据。

执行顺序：

1. 使用固定 digest、生产 Secret 和真实域名部署单实例环境。
2. 验证 HTTPS、HSTS、WebSocket、`/live`、`/ready`，并确认数据库、应用端口和 Prometheus 未暴露公网。
3. 从当前版本或脱敏生产样本执行数据库升级演练，生成符合门禁 schema 的迁移 JSON。
4. 执行生产介质的配对备份和完整恢复，核对：
   - API Key 主体与轮换状态；
   - 配额和用量账本；
   - 财务事件；
   - 审计链；
   - 消息、会话和投递日志。
5. 执行上一镜像回滚，并证明数据库仍与回滚版本兼容。
6. 在生产规格上执行容量测试，记录错误率、p95、实例规格、并发、数据规模和版本。
7. 注入适配器断连、数据库不可用、磁盘告警、积压、账本完整性异常和备份失败，验证告警真实送达值班人员。
8. 对首发平台使用真实账号完成入站、出站、重试和幂等烟测。

退出证据：

- `DATABASE_MIGRATION_REPORT`
- `BACKUP_DRILL_REPORT`
- `ROLLBACK_DRILL_REPORT`
- `LOAD_TEST_REPORT`
- `ALERT_DELIVERY_REPORT`
- 首发平台真实烟测记录
- 连续 7 天无未解释 P0/P1 故障的稳定性报告

### G2：商业运营闭环（可与 G1 并行，3–7 天）

目标：在开发自动计费系统之前，先证明能够合法、清楚地收取第一笔费用并完成客户退出。

执行：

1. 确认经营主体、收款账户、开票/税务处理和退款责任人。
2. 由合格专业人员审查：
   - GPLv3 和第三方依赖的交付方式；
   - 服务条款、隐私政策、DPA；
   - 各 IM 平台对计划用法的限制。
3. 发布 HTTPS 法律页面，建立支持和安全邮箱。
4. 首期选择 `BILLING_MODE=invoice`：
   - 人工合同；
   - 人工收款/开票；
   - 人工开通和停用。
5. 完整演练一次客户生命周期：
   - 创建独立实例和最小权限 Key；
   - 调整套餐配额；
   - 导出客户用量和数据；
   - 吊销全部访问；
   - 删除在线数据；
   - 按保留策略到期删除备份。
6. 确定事故通知、工单升级、暂停服务、退款和终止服务流程。

退出证据：

- `LEGAL_APPROVAL_REPORT`
- `DATA_PROCESSING_INVENTORY`
- `INCIDENT_RUNBOOK`
- 已公开的 Terms、Privacy、DPA
- 支持与安全联系人
- 一次完整客户开通、计量、出账、停用和删除演练记录

### G3：封闭付费试点（30 天）

目标：证明客户愿意付款，同时验证真实运维成本和服务承诺。

范围：

- 只接入 3–5 个设计合作客户；
- 每客户独立 EasyBot 实例；
- 暂不提供自助注册、共享多租户、插件市场和自动支付；
- 每次只扩大一个平台或客户场景。

每周记录：

- 可用性、p95、消息成功率和重复消息率；
- 平台断连、投递积压和恢复时间；
- 工单数量、严重度和首次响应时间；
- 单客户基础设施成本及人工运维分钟数；
- 套餐额度、实际用量、应收和实收；
- 产品缺陷、平台限制、客户配置错误的分别占比。

停止扩张条件：

- 数据丢失、越权访问或账本完整性异常；
- 多客户共同受影响的 P0/P1 缺陷；
- 备份不可恢复或告警未送达；
- 实际成本持续高于套餐毛利且无法通过配置修正。

退出条件：

- 至少 3 个客户完成核心场景；
- 至少 2 个客户真实付款；
- 无未恢复的数据丢失或严重安全事件；
- SLA 达标且支持成本可接受；
- 至少 1 个客户续费或书面确认续费。

### G4：正式公网商用

目标：用现有门禁做最终 Go/No-Go，而不是凭主观判断上线。

执行：

1. 把全部证据路径写入版本控制外的 `evidence.env`，权限设为 `0600`。
2. 先运行离线检查：

   ```bash
   scripts/commercial-launch-gate.sh \
     --offline /secure/easybot-evidence.env launch-offline.json
   ```

3. 在正式域名切流前运行在线检查：

   ```bash
   scripts/commercial-launch-gate.sh \
     /secure/easybot-evidence.env launch-online.json
   ```

4. 只有 `launch-online.json` 中 `passed=true`，且发布、法务、运维和业务负责人共同批准，才开放公网流量。
5. 上线后 72 小时冻结非必要变更，并提高告警与支持值守等级。

## 3. 四周排期

| 周次 | 唯一重点 | 交付结果 |
|---|---|---|
| 第 1 周 | G0 + G1 环境与迁移 | 候选版本、预生产部署、迁移与平台烟测 |
| 第 2 周 | G1 恢复、回滚、容量与告警 | 全部技术证据，连续稳定性观察开始 |
| 第 3 周 | G2 商业运营闭环 | 法律页面、人工计费、客户生命周期演练 |
| 第 4 周 | G3 首批客户开通 | 3–5 个试点名单，首批独立实例和运营周报 |

G3 本身持续 30 天；达到退出条件后再进入 G4。

## 4. 明确暂缓

在 G3 退出前不排期：

- 进程内多租户模型；
- 完整团队 RBAC；
- 自助注册和自动支付；
- 插件市场与不可信原生插件；
- 新增更多 IM 平台；
- 与试点核心场景无关的后台 UI 优化。

支付供应商桥接器只有在人工计费已验证、客户确实需要在线自助支付后才建设。届时复用现有规范化财务事件接口，不把供应商签名验证和原始支付数据塞进 EasyBot 主进程。

## 5. 推进纪律

- 同时在制的 P0 工作最多两项。
- 每项工作必须有负责人、截止时间、验收证据和回滚方式。
- 每周只汇报：当前阶段门、取得的证据、最大阻塞、下一项唯一重点。
- 文档、单元测试和代码存在不能替代真实环境证据。
- 任何重大版本、基础设施、经营主体或法律文本变化后，重新执行商用上线门禁。
